# 监控延迟与企业微信接口评估

本轮按用户选择完成两件事：**停用 Codex 小时健康检查，保留 Windows 本地保活；企业微信仅评估，暂不启用发送。** 当前端到端两秒目标没有达成，不能把每两秒检查当成两秒送达。

## 哪些任务保留

Codex 小时健康检查已设为 PAUSED。它原本只是另做一次状态核查，不参与抓取或提醒。停用后，本地监控、网页记录与正常断线重试继续运行；同时少了这层由 Codex 主动核查异常的补充通知。

下列 Windows 任务保持启用：

| 任务 | 用途 |
|---|---|
| AgentWindowsOperation-WeChatResident | 托盘与读取进程入口 |
| AgentWindowsOperation-WeChatResident-Watchdog | 每分钟及登录后确认托盘在运行 |
| AgentWindowsOperation-WeChatDashboard | 网页服务的启动和保活 |

网页是记录与查看入口；核心采集仍由托盘中的本地程序负责。相关实现：`scripts/wechat_monitor/WeChatResidentTray.cs:159` 的 Ensure，以及 `:369` 的读取进程恢复检查。

## 现有真实提醒的时间测量

读取原 SQLite 中的三条真实提醒，并关联各自通知回执文件的 `atUtc / shown` 事件；没有发送测试消息或重新弹通知。

| 时间段 | 样本数 | 最小 | 中位 | 最大 |
|---|---:|---:|---:|---:|
| 消息自身时间戳 → Windows shown 回执 | 3 | 5.723 秒 | 5.913 秒 | 7.207 秒 |
| 本次轮询起点 → Windows shown 回执 | 3 | 2.057 秒 | 2.799 秒 | 2.805 秒 |
| 进入提醒检查 → Windows shown 回执 | 3 | 1.209 秒 | 1.246 秒 | 1.382 秒 |

测量边界：

- 消息时间戳来自 Alpha 返回的消息记录，本轮三条均为秒级时间。它不是另行测到的“本机微信刚收到消息”的瞬间；发送方时钟、网络与入库等待未单独测量。
- 现有 `first_seen` 是开始轮询时传入的 cutoff，取在两个群的数据读取之前，不是精确的关键词发现时刻。因此“轮询起点到显示”包含查询、解析、落库和通知处理。
- 通知的真实 shown 时刻来自原生助手的事件回执，不采用 SQLite receipts.at_ms 充当 OS 显示时间；后者沿用进入提醒检查的时间。
- `queueBeforeFlushMs` 在原始诊断输出中指轮询起点到提醒检查之间的时间，包含查询和落库，不只指排队。
- 三个样本都是相隔较久的真实提醒。连续密集命中另受 60 秒合并冷却影响，后续提醒可能再等待接近一分钟，不能声称每一条都立即弹出。

补充的短时只读测量：Anode 就绪检查 5 次，中位约 389ms；两群合计读取 6 次，中位约 210ms、最大约 311ms。仅说明这次运行的情况，不代表高峰或长期分位数。

证据：`artifacts/wechat-latency-assessment-20261105-d22a2210/result.json`。复核脚本 `scripts/diagnostics/measure_wechat_latency.py` 已实际运行成功。采集过程中未调用通知、发送或模型接口。

相关代码定位：`scripts/wechat_monitor/resident.py:193` 的轮询与 cutoff；`:208` 的聚合／冷却与提醒预留；`:249` 的就绪检查；`scripts/wechat_monitor/pipeline.py:124` 的每次新建通知助手；`work/anode-fork/src/Anode/Cli/ChatNotifications.cs:40` 的 OS 回执时间。

## 两秒目标怎么理解

当前不能保证“微信收到消息到本机／其他平台显示”在两秒内。即便只看本地流程，2 秒轮询等待再加读取和通知开销，也可能超过目标。

后续可单独改造和验收：

1. 复用已有托盘图标处理通知，减少每次启动通知助手与重复状态检查。当前三个真实样本的提醒处理阶段约占 1.2～1.4 秒。
2. 在用户接受新的读取节奏后，比较 1 秒轮询或经验证的事件源；不把已讨论过的 1 秒性能短测当作账号安全证明。
3. 分开记录“源数据可读”“匹配完成”“发出提醒”“OS／目标平台回执”，按足够样本报告中位和 p95。
4. 明确密集命中的合并策略。首条低延迟和后续合并是两个目标；若要求每条两秒内，需要另改现有 60 秒冷却策略。

Alpha 的官方文档提供 SSE，但本轮没有开启或接入。事件接口也不能自动证明微信入库和目标平台展示满足两秒硬上限。企业微信还包含网络、服务端与客户端通知，需单独实测。

上述改造为方案，**尚未实施／UNTESTED**。当前读取间隔保持用户此前选定的 2 秒。

## 企业微信 CLI 可行性

`WecomTeam/wecom-cli` 文档支持 Windows x64，通过授权机器人向授权人或允许的近期会话主动发送 Markdown、图片、文件、语音和视频。它是本地命令入口，实际调用企业微信服务端；仅安装企业微信桌面客户端，不等于已安装并授权 CLI。

本机检查发现 Node.js v24.14.0；PATH 与 npm 全局安装目录均未找到 wecom-cli / @wecom/cli。不能据此排除其他项目目录的独立安装。CLI 授权状态、实际可发会话、发送成功与目标设备到达时延均为 **UNTESTED**。本轮没有安装、扫码授权、上传或发送。

可采用的扩展结构：授权只读来源 → 本地关键词匹配 → 持久提醒记录 → 独立渠道派发器。看板同时显示本机与企微各自的成功／失败／结果未知。每个渠道单独去重和限流，未知结果不盲目重发，企微故障不阻塞原始抓取。

若后续启用：

- 先核对 CLI 版本与授权，再取本次 identity / sessions 返回的实际目标；不复用旧会话 ID，不假定所有现有企微群都可发。
- 先确定固定接收方、内容范围和频率。可先用“群名、关键词、发现时间”的简短提醒；命中原文、完整 Markdown 和附件另按明确授权处理。
- 文档中的消息命令族是 `message aibot send`；Markdown 上限 20480 UTF-8 字节。具体可用 schema 要以安装授权后的实际 CLI 为准；本轮只验证文档，不宣称本机可调用。
- 文件消息需要先上传取得媒体引用。源群文本仍作为数据处理，不能决定命令、目标或新增工具权限。
- 标准 npm 预编译版本默认向企微回传 Agent 程序名及调用链信息；这是项目数据收集说明明确列出的行为，不能声称整个通知链路的数据永远只留本机。

本地的消息技能缺少公共前置文件，本轮已从该仓库的正式技能文档读取公共规则作评估参考；未调用 wecom-cli 业务命令。

参考：[README](https://github.com/WecomTeam/wecom-cli/blob/main/README.md)、[CLI 参考](https://github.com/WecomTeam/wecom-cli/blob/main/docs/cli-reference.md)、[消息技能](https://github.com/WecomTeam/wecom-cli/blob/main/skills/wecomcli-message/SKILL.md)、[公共前置检查](https://github.com/WecomTeam/wecom-cli/blob/main/skills/wecomcli-shared/SKILL.md)、[数据收集说明](https://github.com/WecomTeam/wecom-cli/blob/main/docs/data-collection.md)。
