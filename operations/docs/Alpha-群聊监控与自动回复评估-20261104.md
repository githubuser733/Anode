# Alpha 群聊关键词监控、总结和自动回复评估

结论：可以基于现有接口构建只读关键词监控、本机提醒和自动总结。监控程序不需要另外向微信注入代码。**目前不能把 Alpha 从获取密钥、连接微信到自动发送的整条链路，认证为“完全非 Hook、低账号风险”。** 发送工具存在，但发送连接的底层机制、实际送达与长期稳定性尚未验收。本轮仅做分析和只读核验，没有启用主动推送、捕获微信登录材料、调用模型总结私聊内容或发送消息。

这里的 Hook 指修改或挂接微信内部执行流程；MCP 只是调用入口，无法保证它调用的软件内部采用什么方式。Alpha 提供的 API 也不等于腾讯官方群机器人接口。是否使用 Hook、是否会误发、是否会泄露群内容、是否稳定运行，是四个不同问题。

## 本机执行证据

2026-11-04，使用已有本地令牌访问 `127.0.0.1:5031`。令牌仅在内存中使用，没有输出。调用链为本地 Python → Alpha HTTP `/mcp`，不代表已经把 Alpha 注册成当前 Codex 的原生工具。

- `GET /api/v1/push/status` 返回 HTTP 200，`source=engine.read_only_polling`，`pollIntervalMs=2000`，`transport=sse`。
- 当前 `enabled=false`，没有开启订阅。上限为 8 个订阅者、每轮 128 个活跃会话，重叠观察窗口为 60 秒；`replay=false`，超出窗口的迟到消息不保证被观察。
- 本机 `/mcp` 的 `tools/list` 实际返回 31 个工具，含 `wechat.chat.send_text` 和 `wechat.chat.get_send_status`。公开文档列出的工具总数更多，不能直接套用文档数量。
- 已实际调用只读工具 `wechat.chat.get_messages` 并取得结构化结果；不仅检查了工具清单。仅请求一条记录，未记录正文。发送、密钥采集调用次数均为 0。
- 校验输出为 `ALPHA_MONITOR_READONLY_PROBE_OK`，见 [readonly-probe.json](../artifacts/alpha-monitor-assessment-20261104-db54e7ec/readonly-probe.json)。

2 秒是该服务报告的轮询周期，不是“微信收到消息到通知弹出”的实测延迟。数据库落盘、查询排队和通知系统都会增加时间。SSE 实流、新消息／撤回、断线补读和全天稳定性均为 **UNTESTED**。

## 非 Hook 能证明到哪里

### 读取与监控

作者说明普通读取以只读方式打开微信数据库；本机推送状态也明确报告只读轮询。这支持“在原 Alpha 已能读取数据的前提下，监控层复用读取接口，不新增微信 Hook”的方案。[作者说明](https://github.com/xunchahaha/alpha-releases/blob/09232cbca892241fd3d2046957832a6b4d764ddc/README.md#隐私说明)

但初始化密钥与持续读取应分开判断。安装包主进程提供 `auto`、`memory-scan`、`runtime-capture` 三种数据库密钥获取模式；对应源码提取见 [alpha-main-index.js](../artifacts/alpha-monitor-assessment-20261104-db54e7ec/alpha-main-index.js)。静态字符串检查在 `alpha_xkey.dll` 和 helper 中发现 `ReadProcessMemory`；**读取进程内存不等同于 Hook**，也不能据此证明或否定运行时捕获路径是否注入。字符串扫描不是完整二进制审计，没有发现某个名字也不能证明相关行为不存在。

如果要求连初次获取密钥都不接触微信进程，当前已有的 Anode UI Automation 监控更适合作为保守起点：它读取窗口辅助功能树，再本地匹配关键词，不需要 Alpha 的数据库密钥。已读源码 [ChatTextReader.cs](../work/anode-fork/src/Anode/Cli/ChatTextReader.cs) 的 `Read` 从 `AutomationElement.FromHandle` 获取消息列表。代价是依赖群窗口和辅助功能可见范围，多群切换、长历史与漏读恢复不如数据库接口方便。

### 自动发送

公开文档要求激活发送功能，并先在高级功能中连接微信。本机源码进一步显示：`ExternalTextSend.send` 要求可用的发送 bundle；`startMaterialCapture` 交给原生组件解析账号对应的微信进程，完成采集后才保存本次运行使用的发送 bundle。首次可能下载组件并检查许可。因此不能把一次 HTTP POST 等同于在微信输入框内正常按发送。相关代码见本次源码提取的第 3250、3268、63155、63228、63286 行。

本轮没有启动这条采集／发送流程，也没有审计动态发送组件。**不能断言它使用 Hook，也不能断言它完全没有 Hook。** 本机发送工具的出现只证明接口已暴露，不证明授权、连接或送达可用。

0.3.5 发布说明确实说已移除旧的、基于微信钩子的原图自动下载功能，但这个声明范围仅限那个旧功能，不能扩大成所有组件无 Hook。[0.3.5 发布说明](https://github.com/xunchahaha/alpha-releases/releases/tag/v0.3.5)

若“由官方微信客户端界面完成发送、我们不调用微信私有内部函数”是硬要求，可以另做 Anode UIA／键鼠发送执行器；该发送执行器尚未实现或实测，且仍需解决目标群核对、焦点变化及误发问题。非 Hook 不能推出零账号风险。

## 推荐的工作方式

| 功能 | 推荐处理 | 关键边界 |
| --- | --- | --- |
| 群关键词提醒 | 常驻本地程序读取 HTTP 数据，匹配关键词／规则，向主桌面弹通知 | 匹配不调用模型，不向群发送；提醒可复用已有通知队列 |
| 自动群摘要 | 按指定群和时间段收集增量，分批交给模型，保存摘要与原消息引用 | 只处理指定群；摘要与未核实推测分开；没有消息则不生成 |
| 摘要回群 | 独立发送执行器只接受固定群与已审核规则输出 | 初期可人工确认；全自动时设触发条件、频率／日上限、停止开关和持久发送记录 |

常驻数据采集优先 HTTP/SSE；MCP 用于按需读取、查询状态和管理任务。这样无需让大模型每 2 秒发一次工具调用。关键词匹配本身没有模型 token 成本；摘要的 token 用量取决于进入模型的消息量。原 Alpha 仍需保持打开和解锁，接口关闭／锁定后监控必须显示离线，不能继续报“运行正常”。

Alpha 自带 AI 总结在 0.3.5 中已有“群聊精华”风格，但公开 HTTP/MCP 文档没有给出“定时总结并自动回群”的一体化接口，需要外部常驻程序编排读取、模型和发送。群消息被提交给云端模型时会离开本机；若要求本地处理，应选本地模型。原有独立模型桥接可以作为候选，但本轮未重新验证模型推理或应用内自动总结，均不能当作已部署。

现有监控可复用“本地关键词匹配、通知队列、持久事件／通知记录”的设计；数据读取器需另接 Alpha，不能只把旧 UIA 采集器的路径换一下。旧实现见 [watch-chat-monitor.py](../work/anode-integrated-20261104-031349-f64226/publish/monitor/watch-chat-monitor.py) 第 266、319、447、459 行。

## 达到低风险需要的具体条件

1. **可靠采集**：指定群白名单；启动只建立当前位置，不把历史当新消息轰炸提醒；SSE 断开后补读。先验证 SSE `rawid` 与补拉消息 ID 的对应关系，再按账号、群、消息身份去重。持久化检查点，处理迟到和撤回；覆盖出现缺口时明确提醒，不能承诺零漏消息。
2. **读写隔离**：当前 5032 只读副窗口代理继续保持只读。监控、摘要服务不应取得可发送的任意工具入口；新增推送转发时也只放行固定读取路径。Alpha 原始令牌兼具读和发送权限，不给网页或模型直接持有。
3. **限制模型权限**：群消息只作为待总结数据，消息中“忽略规则、转发文件、改群、调用工具”等文字不能改变任务配置。模型只生成草稿文本与来源，不决定收件群、不更改白名单；接收者由固定配置决定。
4. **防误发与循环**：按固定时间段或明确触发命令出摘要，排除本程序发出的消息，设置每群发送间隔、日上限和一键停止。先按只读方式观察，再在另行授权的测试群验收发送。不能将关键词提醒默认发回所有群。
5. **防重复发送**：保存摘要批次、目标、正文哈希、幂等键和 `run_id`；超时、`unknown` 或未确认状态先查询，禁止盲目重试。官方幂等键只在 Alpha 本次运行期间保留，重启后仍需自己的持久发送记录。发送成功还要区分微信送达与本地记录写入结果。[HTTP 发送约定](https://github.com/xunchahaha/alpha-releases/blob/09232cbca892241fd3d2046957832a6b4d764ddc/docs/api/http-api.md#发送文字消息)

推送存在公开未关闭问题 `push.message_invalid`。这是稳定性验证的依据，不代表本机已经复现；同时 0.3.5 宣布除必要组件／安全更新外主要停止功能维护。长期运行必须安排错误恢复与回归验证，不能凭一次 HTTP 200 宣称完成。[Issue #25](https://github.com/xunchahaha/alpha-releases/issues/25)、[发布说明](https://github.com/xunchahaha/alpha-releases/releases/tag/v0.3.5)
