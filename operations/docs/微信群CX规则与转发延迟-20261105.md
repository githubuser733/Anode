# CX 业务筛选及转发延迟

已按用户最新条件启用 **CX 每人恰好 8.8 万规格，人民币单价每万不少于 985 元**。条件不足的消息保留为“业务待核实”，明确不符的保留为“不符合业务规则”，两者都不触发本机提醒或企微发送。其他不含 CX 的消息沿用原关键词规则。真实新增 CX 报价到企微手机的到达时延、长期误判率和重启后的全天稳定性仍为 **UNTESTED**。

## 目前是一条就转发，还是合并

原采集器每 2 秒查询两个白名单群，先在本地匹配“收”或“UA”，再应用业务规则并保留原始记录。企微转发器每 2 秒读取同一 SQLite，没有第二个微信采集器。

距离上一次派发已满 60 秒时，新合格消息在下一轮转发检查就可发送，不会故意再攒一分钟。距离上一次派发不足 60 秒时，后续合格命中留在持久队列，等冷却结束合并发送。它不是“每条立刻发”，也不是“每条固定延后 60 秒”。超长原文分段后每批最多 12,000 UTF-8 字节，剩余分段会继续排队，突发大量消息可能等待多轮。

发送前重新核对机器人和授权收件人，并持久预留发送记录。接口接受后记录 accepted；结果不确定或明确拒绝时停止后续派发等待核对，禁止盲目重发。规则启用前已排队而未发送的内容也会重新判断；被规则挡下的分段追加 suppressed 回执，不进行外部调用。旧正文、分段、消息及发送回执没有被删除。

实现入口：`scripts/wechat_monitor/business_rules.py:32` 解析报价，`:79` 决定是否允许提醒；`scripts/wechat_monitor/resident.py:145` 在分页限制前过滤、`:217` 派发本机提醒；`scripts/wechat_forward/forward.py:315` 入队、`:343` 发送前复核、`:360` 执行冷却及派发；`scripts/wechat_dashboard/data.py:168` 保留历史回执并显示当前业务状态。实际参数在 `config/wechat-business-rules.json` 和 `config/wechat-wecom-forward.json`。

## 规则边界

| 原文示例 | 结果 | 原因 |
|---|---|---|
| 收CX3万 960/万 | 不提醒 | 数量及价格不符 |
| 收CX6万 1000元/万 | 不提醒 | 最新要求为每人 8.8 万，不再是 6 万以上 |
| 收CX每人8.8万 985元/万 | 提醒 | 数量恰好相等，单价包含 985 的边界 |
| 收CX8.8万 984.99元/万 | 不提醒 | 单价低于阈值 |
| 收CX两人合计17.6万 990元/万 | 待核实 | 不用总量除人数来猜单人规格 |
| 收CX共17.6万，每人8.8万，990元/万 | 提醒 | 明确给出每人规格 |
| 收CX8.8万 @1000 | 待核实 | 未说明每万单位，不能把裸数字当单价 |
| 一段含多个品种、不同价格或规格 | 待核实 | 避免把一条的价格和另一条的数量拼在一起 |

本地规则使用 Decimal、明确单位和文本模式；支持大小写、全角写法、万/w、千/k、明确积分数量、每万或每分价格及明确每人说明。只识别明文 CX，尚未扩展其他别名、图片 OCR、语音或完整自然语言理解。含范围、币种混用、无法对应的多价多规格等转入待核实，不调用云端模型猜测。原文指令不能修改阈值、接收人或工具权限。

只要仍然命中原关键词，原始记录继续保存到看板；此规则不会新增 CX 为独立关键词，所以没有“收”或“UA”的消息仍按原采集口径处理。已发生的历史通知保留原回执，即使当前规则重新评价时不符，也不会把历史事实改写为未提醒。

## 实测延迟

2026-11-05 本机有界测量，未发送任何新测试消息、未调用模型：

| 阶段 | 实测结果 | 范围说明 |
|---|---|---|
| 两个群的 Alpha 只读查询 | 中位 221.52ms，118.30～291.14ms | 6 轮；数据已由 Alpha 可读，不等于微信实时同步延迟 |
| Anode ready 检查 | 中位 391.11ms | 5 次；只是本机通知预检 |
| 新增 CX 判断，短报价 | 中位 0.0135ms，P95 0.0287ms | 6,000 次本地样例；最大 1.6931ms |
| 新增 CX 判断，10,216 字文本 | 中位 2.8004ms，P95 3.96ms | 100 次；最大 4.4298ms |
| 既有企微首批发送命令 | 1,375ms | 仅 1 批历史补转；不含前置身份核对与轮询，也不等于手机到达 |
| 既有消息时间戳至本机系统 shown | 5.64～7.21 秒，中位 5.82 秒 | 6 条既有真实回执；消息时间戳不是精确本机到达时刻 |

因此加这两个本地数字条件几乎不会增加秒级延迟。空闲时整体仍要经过采集最多约 2 秒的轮询等待、Alpha 读取、转发器另一次最多约 2 秒的等待，以及身份核对和 CLI 发送。密集时再叠加冷却；目前不能保证两秒内到企微手机，真实微信→Alpha 同步、网络及手机通知时延尚未测到。

证据：`artifacts/wechat-cx-timing-fb9c7f6a/result.json`、`artifacts/wechat-latency-assessment-20261105-c2de70c8/result.json`。早先测量曾因 Alpha 已退出而出现 ConnectionRefusedError，后又遇到 Anode 正在重连导致 NOTIFIER_ANODE_NOT_READY；恢复 Alpha 并等宿主 ready 后，同一诊断入口已实际成功。失败不算新的性能样本。

## 优化空间

1. 对追求速度的通知策略，最大的可见延迟来自 60 秒合并冷却；可改成“首条立即、很短窗口合并后续、设每分钟总量上限”。这会增加企微消息频率，需要用户另选节奏，本轮没有擅自降低冷却。
2. 可在采集写入后通知转发器，减少第二层 2 秒定时等待，同时保留 SQLite 断线恢复和去重。当前是两个独立进程，需要实现并实测可靠的唤醒路径；尚未实施。
3. 可再分析身份查询、CLI 子进程启动和落盘耗时；不能为了省时取消接收人核对或“发送前落盘”。
4. 原生通知处理目前与同一轮读取串行；可拆分通知与读取，避免弹窗期间拖慢下一轮。需重新验证通知单实例和 unknown 回执，当前未改造。

比把价格比较交给云端模型更合适的是保留本地规则，并对明确已解析字段比较。以上是后续可选改造，没有把推算称为已实现的两秒送达。
