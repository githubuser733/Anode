# 微信群托盘与检查频率

当前已切换为原生托盘后台程序，用户选择的节奏是 **每 2 秒检查、首次发现命中立即请求本机提醒**。后台仍只读取两个指定群，不发送微信、不操作键盘、不调用摘要模型。数据目录和原读取进度保持连续。

## 日常使用

项目：`F:\AI infrastructure\agent-Windows-operation`。

1. 双击 `launchers\微信群关键词提醒-托盘.lnk`。程序在主桌面的通知区运行，可能收在右下角“^”里；悬停文字为“微信群关键词提醒”。
2. 右键菜单提供“查看状态”“暂停监控／恢复监控”“打开报告目录”“打开日志目录”“测试本机提醒”“退出并停止监控”。双击图标查看状态。
3. 暂停会正常停止读取、停用定时保活并保留图标。退出会同时退出托盘。之后显式恢复或重新打开启动入口才能再次启用。
4. 原“微信群关键词监控-启动／停止”快捷方式继续可用，但目标已改为原生 GUI EXE。`WeChat-Resident.cmd` 保留给终端诊断，日常使用托盘快捷方式。

只读来源仍为“星创票务 收分群”与“✈️方舟航空✈️壹”，关键词“收”或“UA”。UA 忽略大小写，以英文字母为边界；`UA1000` 也匹配。历史进度、去重库及报告继续保存在 `artifacts\wechat-resident`。

首条命中不再等待原来的 20 秒聚合。同一分钟内后续命中会保留并合并到下一次通知，避免密集弹窗。2 秒是检查目标周期，不是微信收到消息到屏幕提示的延迟保证；数据库落盘、Alpha 查询与 Windows 通知仍会增加时间。

## 1 秒是否安全

作者说明普通读取以只读方式打开本机微信数据库；HTTP 服务只监听本机。当前读取器仅允许两个只读 MCP 工具，没有启用微信发送或新增 UI 点击。这支持“缩短间隔主要增加本地查询负载”的判断，但不能把 Alpha 的完整链路或某个频率认定为腾讯认可的安全方式。[Alpha 隐私说明](https://github.com/xunchahaha/alpha-releases/blob/main/README.md#隐私说明)、[本机 HTTP API](https://github.com/xunchahaha/alpha-releases/blob/main/docs/api/http-api.md)

本轮有界短测在现有监控继续运行时进行，没有保存消息正文、没有发送消息：

| 观察阶段 | 次数 | 两群合计每轮读取中位 | 最大单轮 | Alpha 相关进程累计 CPU／墙钟时间 |
|---|---:|---:|---:|---:|
| 10 秒周期 | 3 | 219ms | 234ms | 约 0.17 个 CPU 核心 |
| 1 秒周期 | 30 | 203ms | 953ms | 约 0.40 个 CPU 核心 |

1 秒阶段 p95 为 547ms；共调用只读接口 71 次。两段均未读到所选近 5 分钟窗口内的消息，因此这是一组空闲数据上的分时观察，不能当作高峰性能、真实命中时延、长期稳定性或账号风险的证明。CPU 数字也不是整机百分比，更不是严格控制变量后的性能倍数。

用户据此选择 2 秒。没有改动 Alpha 的主动推送设置；官方 SSE 仍可作为以后优化选项，但此次没有接入或声称已验收。

短测原始数据：`artifacts\wechat-poll-benchmark-8f8f249601\result.json`。

## 黑框与托盘实现

旧计划任务使用控制台 PowerShell 作为入口，即使请求隐藏，实测触发时仍观察到一个新 Windows Terminal 窗口。同一状态查询通过 `CREATE_NO_WINDOW` 子进程运行没有复现，问题缩小到旧计划任务的控制台启动层；不能由此断言机器上所有其他黑框都来自该任务。

现在工作任务与每分钟保活任务直接调用 `WeChatResidentTray.exe`，PE 子系统验证为 `2 / Windows GUI`。托盘通过明确的无控制台进程参数启动 Python 读取器，保留单实例锁、进度、断线恢复和正常停止。控制脚本也改为显式捕获子进程输出，不再依赖 `-WindowStyle Hidden` 避免控制台创建。

- GUI 进程入口、状态与菜单：`scripts/wechat_monitor/WeChatResidentTray.cs:273`。
- 子进程无窗口参数：`scripts/wechat_monitor/WeChatResidentTray.cs:113`；主桌面读取器启动：`:169`。
- 原有 CLI 兼容入口：`scripts/Control-WeChatResident.ps1:6`。
- 活动二进制、Python 路径与哈希：`config/wechat-resident-tray.json`；轮询参数：`config/wechat-monitor.json:14`。

核心监控与 Windows 保活不依赖 Codex 对话持续打开。辅助的 Codex 小时健康检查已按用户要求于 2026-11-05 停用；原 Windows 本地保活继续运行。

## 实际验证与剩余边界

- C# 编译通过，GUI 子系统为 2，运行位置为主桌面 Session 1。
- 33 项行为测试通过，包括首次立即提醒、后续冷却保留、分页、重连、去重及读取进度。
- 实机验证通过：只有一个托盘与一个读取器；暂停后保活不擅自恢复；恢复后原激活时间不变、检查点不倒退；正常退出后无托盘／读取进程；重新启动由原生计划任务恢复。
- 托盘版 2 秒检查的实测中位周期约 1.984 秒（4 个间隔样本）；持续时间很短，不扩大为长期保证。
- 明确标注模拟的本机通知获得 `shown` 回执，标识 `WKR-f1e44b10942e`。这不等于用户已经阅读通知。
- 22:52 的运行日志另外记录了托盘“测试本机提醒”菜单处理器的实际执行，标识 `WKR-c25aa5c101d6`，也返回 `shown`；不是仅验证命令行入口。
- 首次替换后的 12 秒保活触发测试、随后包含启停／通知的连续 60 秒观察，均未发现新的可见控制台窗口。采样间隔 10ms，不保证发现所有短于采样间隔的窗口。

实机结果：`artifacts\wechat-tray-live-7950db4190\result.json`；黑框前后对照：`artifacts\wechat-console-probe-4bf9ad99d1`、`artifacts\wechat-console-probe-c45b9c3026`。旧脚本、配置、快捷方式及任务 XML 备份在 `artifacts\wechat-tray-deploy-20261104-7ac5be1a`。

仍为 **UNTESTED**：电脑重启／Windows 重新登录后的实际恢复、全天稳定性、真实关键词命中至弹窗的延迟，以及其余菜单和状态窗口的人工点击体验。启停测试已实际执行对应无窗口控制命令；没有为测试去点击用户的主桌面，也没有重启电脑。输入法冲突排查继续暂停。

## 自行复核清单

- 打开托盘快捷方式，悬停应看到“微信群关键词提醒 · 正在监控”；右键查看状态应显示 2 秒检查、两个指定群。
- 在项目终端运行 `.\launchers\WeChat-Resident.cmd Status`，应看到 `enabled/running/healthy=true`。
- 右键“测试本机提醒”，应出现明确标注测试的本机通知；测试报告单独保存，不发送到群。
- 右键暂停，稍后状态应为暂停；恢复后读取继续。退出菜单应连同图标和读取进程一起停止。
- 行为回归：`python -X utf8 -B -m unittest discover -s scripts/wechat_monitor -p "test_*.py" -v`，当前预期 33 项、`OK`。
- 有界实机验收：`python -X utf8 -B scripts/diagnostics/test_wechat_tray_live.py`，会短暂暂停／恢复监控并显示一条模拟提醒，结束后恢复运行，预期 `TRAY_LIVE_ACCEPTANCE_OK`。
