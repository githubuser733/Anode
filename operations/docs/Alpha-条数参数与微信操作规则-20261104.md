## 风险比较

若最看重减少对微信内部实现的接触，优先采用 Anode UI Automation 只读窗口 → 本地关键词提醒 → 摘要草稿 → 授权后通过原生界面发送。已读采集代码通过 `AutomationElement.FromHandle` 和消息列表读取窗口，见 [ChatTextReader.cs:119](../work/anode-fork/src/Anode/Cli/ChatTextReader.cs)。这个判断针对读取机制，不保证封号概率，也不证明整个 Anode 或所有微信操作都无风险。

多群、长历史补读使用 Alpha 已有只读 HTTP/MCP 更方便；但从密钥获取到连接／发送的整条链路尚未完成非 Hook 审计。MCP 和 HTTP 若调用同一后台，不会因协议名称不同就自动降低风险。单次读取 100 条是查询批量大小，与向微信发送 100 条消息不同。

## “接口暴露”与“发送已解锁”

1. 本项目 `127.0.0.1:5032` 代理仅允许账号、会话、消息、搜索 GET，没有发送路由；见 [server.py:32](../scripts/alpha_readonly/server.py)。
2. 原 Alpha `127.0.0.1:5031` 的实际 MCP 清单含 `wechat.chat.send_text` 和 `wechat.chat.get_send_status`，原生 HTTP 也定义 `/api/v1/messages/send-text`。接口确实存在；“没有暴露”不准确。
3. 官方文档还要求激活“发送文字消息”，并在高级功能连接微信。未激活为 403，未连接为 409 `SEND_CONNECTION_REQUIRED`。接口列出不代表本机满足这两个条件，更不代表有常驻程序在自动发送。见 [发送准备与错误约定](https://github.com/xunchahaha/alpha-releases/blob/09232cbca892241fd3d2046957832a6b4d764ddc/docs/api/http-api.md#发送文字消息) 和 [bundle 检查:3268](../artifacts/alpha-monitor-assessment-20261104-db54e7ec/alpha-main-index.js)。
4. 本轮没有调用发送端点来探测权限，也没有激活或建立发送连接；本机当前发送许可／连接是否可用仍 **UNVERIFIED**。不能断言“已解锁”，也不能仅凭未测试就断言“未解锁”。原 API 令牌不交给模型或副窗口，继续保留只读隔离。
