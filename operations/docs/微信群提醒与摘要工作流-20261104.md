已完成指定两群的真实读取、关键词匹配、模型摘要、Windows 提醒，以及 Anode 微信原生界面投递。**Alpha HTTP API 与 MCP 发送均因 `SEND_CONNECTION_REQUIRED` 被拒绝，没有发出测试消息。** 原生投递成功一条；没有向任何群发送。

当前交付为可复用的限时工作流，没有安装开机常驻或定时发送。真实群观察的两段窗口（60 秒、90 秒）都没有新增消息，因此新消息网络到达后的通知延迟、长期漏报率及全天运行仍为 **UNTESTED**。

## 工作流与实现

`Alpha 本机 HTTP /mcp 只读工具 → 本地关键词匹配与去重 → 已配置模型桥摘要 → 本地草稿 → 显式 Anode MCP 操作微信原生界面 → Alpha 只读回读核验`

- [运行配置](../config/wechat-monitor.json)：群白名单、关键词、最近记录数量、分页／分批预算、模型连接文件、通知目标。
- [读取与模型适配器 clients.py:17](../scripts/wechat_monitor/clients.py)：读取适配器只放行已核实的读取工具和群 ID；不调用 Alpha 发送端点。每页最多 200，游标页保持相同时间边界，分页停滞或覆盖超过本轮预算时报错，不静默跳过。
- [匹配与分批 core.py:36](../scripts/wechat_monitor/core.py)：按群与消息 ID 去重，每个摘要批次最多 3000 条且序列化输入最多 90000 字符；单条超预算直接报错，不偷偷截断。多个批次先各自摘要，再归并摘要，保留来源引用。
- [流程 pipeline.py:24](../scripts/wechat_monitor/pipeline.py)：`prepare` 生成历史回放提醒和摘要草稿；`watch` 每 10 秒读取，结束时合并本轮命中并弹本机通知；`--summarize-new` 在本轮确有新增时再生成一份最近记录摘要，不逐条调用模型。
- [发送 native_delivery.py:170](../scripts/wechat_monitor/native_delivery.py)：只接受本项目已生成且哈希一致的草稿，固定 filehelper，核对标题及输入框，已有草稿则停下。先持久化发送预留，再输入与点击；文字禁止换行／Tab 等会被 Anode 转成按键的控制字符。发送结果未知不重试。通过微信 UI 和 Alpha 两条路径验证实际正文。
- [状态 core.py:112](../scripts/wechat_monitor/core.py)：项目内追加日志，不删除原记录。监控与发送分别使用 Windows 文件锁，拒绝并发运行；正常退出释放锁但保留锁文件。常规原生投递冷却 3600 秒，是本项目防重复策略，不是微信官方安全阈值。

MCP 调用来自 Alpha 本机 `5031/mcp`，Anode 使用已有全局本地 stdio 入口；没有把 Alpha 包装成一个并不存在的新 Codex 插件。业务代码、配置和证据均在本项目，不修改 Alpha 安装包或 Anode 核心程序。

摘要使用已配置的 `http://127.0.0.1:7656/v1` 模型桥和 `gpt-6.1-terra`。该桥会连接模型服务，不能把它称作群文本完全不上云。桥的 `tool_choice=none` 只禁止传入的客户端工具，不证明 Codex 内置工具被彻底隔离；本工作流不给模型传 Alpha／Anode 令牌，不执行模型返回的工具调用，严格检查群 ID 和引用，并在实际投递前检查摘要。模型工具隔离并未因此获得完整安全认证。

## 日常使用与复核

保持原 Alpha 已打开并解锁；需要发送时，微信应已登录在 Anode，投递期间避免人工同时操作该输入框。以下命令在项目根目录运行，或对入口使用绝对路径。

1. 不读聊天、不发消息的行为检查：

```powershell
python -X utf8 -B .\scripts\wechat_monitor\test_monitor.py
```

预期 `Ran 15 tests` 与 `OK`。测试证据留在项目 artifacts，不自动删除。

2. 生成最近记录的提醒／摘要草稿（会读取指定两群并调用已配置模型）：

```powershell
.\launchers\WeChat-Monitor.cmd prepare --count 100
```

预期 `WECHAT_DIGEST_PREPARED` 和本次输出目录。打开其中 `delivery.txt` 检查内容；默认不发送。需要更多记录时显式增加 count，每群最多 30000，模型批次预算默认 10；不要把任务总量和每批 3000 条混为一谈。

3. 限时观察 60 秒；有新增才生成最近记录摘要，命中才合并弹本机提醒：

```powershell
.\launchers\WeChat-Monitor.cmd watch --seconds 60 --summarize-new
```

预期 `WECHAT_BOUNDED_WATCH_OK`，无新增时 `newMessages=0`，不调用模型。首次或重新启动从当前时点建立基线，不把历史当新消息轰炸提醒；停机时间段完整补读尚未实现。运行期间可在本次输出目录新建空文件 `STOP` 请求停止，不强杀微信或 Anode。

4. 已确认某份草稿且有本次原生发送授权后，将下方 `<本次输出目录>` 替换成真实目录：

```powershell
python -X utf8 -B .\scripts\wechat_monitor\native_delivery.py '<本次输出目录>' --send-reviewed
```

预期 `WECHAT_NATIVE_SEND_VERIFIED`。同一份已经尝试的草稿会被拒绝再次投递；不要对本次已成功目录重跑来验证。直接在文件传输助手搜索 `WXM-239612853e`，应找到本次一条测试摘要。

这条流程减少了反复切群、滚动、复制等界面操作；自动点击仍然是自动化，不能据此承诺避开机械化判定。持续发送、频率优化、长期新消息连续性和更强的模型隔离均未作为本次实测成功事项。
