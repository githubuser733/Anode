# UU 主桌面兼容模式

**当前组合已实测可用：UU 访问原始主桌面，Anode 子会话继续运行。ToDesk 尚未解决。**

2026-11-03，用户先确认 UU 仍进入 Anode 子桌面。将 UU 采集进程固定到物理主会话后，用户重新连接确认已回到原始桌面；随后又执行了恢复默认行为、重新启用、断开重连，用户最终确认“主桌面正常，键鼠也正常”。这是当前运行环境下已验证的绕过方案，尚未验证电脑重启、UU 升级、锁屏及 Anode 子会话重建。

## 日常入口

先让 Anode 按原来的方式运行，然后打开以下入口并允许 Windows 管理员提示：

- [启用 UU 主桌面模式](<F:/AI infrastructure/agent-Windows-operation/launchers/UU-Console-Enable.cmd>)。首次启用会短暂断开 UU；已经处于本模式时，重复点击不会重新启动采集进程。
- [恢复 UU 默认行为](<F:/AI infrastructure/agent-Windows-operation/launchers/UU-Console-Restore.cmd>)。这会恢复 UU 自己的会话选择；Anode 存在时可能再次进入子桌面。它不是“回到主桌面”按钮。
- [日常入口脚本](<F:/AI infrastructure/agent-Windows-operation/scripts/Set-UUConsoleMode.ps1>)支持 `Status`、`Enable`、`Restore`，默认 `Status` 只读。

没有安装开机任务。重启电脑或 UU 服务后，如果再次进入子桌面，重新执行启用入口。脚本限定本次核对过的 UU 服务二进制哈希；UU 更新后若拒绝执行，需要重新核对新版本，不能直接移除版本检查。

## 为什么会发生

Anode 确实创建了独立的 Windows 子会话：源码设置 `ConnectToChildSession=true`，不是普通的多显示器切换。见 [RdpViewer.cs:149](<F:/AI infrastructure/agent-Windows-operation/work/anode-fork/src/Anode/Daemon/RdpViewer.cs:149>) 和 [微软 Child Sessions 文档](https://learn.microsoft.com/en-us/windows/win32/termserv/child-sessions)。

本机 UU 版本为 `4.45.0.4318`。未取得厂商 C++ 源码；下面依据安装文件的只读反汇编，不能冒称为厂商提供的源码。

服务文件：`C:\Program Files\Netease\GameViewer\GameViewerService.exe`。

SHA256：`708fcc3a953aa7952cdf6c59a793314618636aaffdc8b2b3e0979c2b6a0e97e6`。

它的会话选择分支可概括为以下伪代码：

```text
selected = INVALID
for each session returned by WTSEnumerateSessionsW:
    if session.State == WTSActive:
        selected = session.SessionId

if selected == INVALID:
    selected = WTSGetActiveConsoleSessionId()
```

也就是保留枚举到的最后一个活动会话，只有没有活动会话时才使用物理控制台。参见 [活动会话遍历:64](<F:/AI infrastructure/agent-Windows-operation/artifacts/uu-session-investigation-20261103/service-session-disassembly.txt:64>)、[物理控制台后备分支:88](<F:/AI infrastructure/agent-Windows-operation/artifacts/uu-session-investigation-20261103/service-session-disassembly.txt:88>) 和 [调用跳转核对:2](<F:/AI infrastructure/agent-Windows-operation/artifacts/uu-session-investigation-20261103/service-control-disassembly.txt:2>)。

现场 Windows 报告物理控制台为会话 1，Anode 子会话为 6，而 UU 的 `GameViewerServer.exe` 位于会话 6。会话号会随登录变化，脚本每次通过 Windows API 读取，不把 1 写死。API 含义见 [微软 WTSGetActiveConsoleSessionId 文档](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-wtsgetactiveconsolesessionid)。

## 本次绕过的做法

1. 核对安装文件哈希、进程路径、原启动参数和微软 PsExec 签名。
2. 使用当前 UU 服务内部已核对的控制码 `130` 暂停自动拉起进程；原服务仍运行。
3. 使用 UU 自带的 `PsExec64.exe`，保持工作进程的 SYSTEM 身份，将原版 `GameViewerServer.exe` 与 `GameViewerHealthd.exe` 启动到物理主会话。
4. 验证两进程位于主会话、Anode 进程与会话未变，然后保留运行状态。
5. 恢复时，只终止本次启动且 PID、创建时间、路径均匹配的进程，再用控制码 `131` 恢复 UU 自动管理。

控制码是本版本的内部行为，不是 UU 公布的兼容 API。[控制码映射及管理循环证据](<F:/AI infrastructure/agent-Windows-operation/artifacts/uu-session-investigation-20261103/service-supervision-disassembly.txt:1>)。PsExec 的 `-s` 与 `-i` 含义已对照 [微软文档](https://learn.microsoft.com/en-us/sysinternals/downloads/psexec)；实际调用日志保留在每次试验目录。

没有修改 UU 安装二进制、应用配置或服务启动类型，也没有停止、重启或注销 Anode。暂停 UU 自动管理后，工作进程异常退出不会按原方式自动重建，可重新执行启用入口恢复。正式上游修复应调整 UU 的目标会话选择，而不是依赖此运行时管理方式。
