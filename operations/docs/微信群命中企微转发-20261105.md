当前企微转发已经启用。已把现有 6 条真实命中合并为一批，通过已授权的“狐狸的机器人”发给授权本人“张虹”；官方 CLI 返回业务成功，持久账本记录 1 批 accepted。接口接受不等于手机到达或本人已读。真实新消息从微信进入 Alpha 再到企微的完整时延、电脑重启和全天稳定性仍为 **UNTESTED**。

## 范围与内容

- 来源仍仅为“星创票务 收分群”和“✈️方舟航空✈️壹”；关键词为“收”或“UA”，沿用现有本地匹配规则。旧“美卡101星球-会员群1”不在白名单内。
- 转发每条已抓取命中的群名、发言人、消息时间、发现时间、命中关键词、消息类型和完整文本。使用 Markdown 分块排版，不调用摘要模型，不把原文改写成摘要。
- 首次把本机现存命中标为“历史命中补转”；之后按消息标识去重，重启继续进度。原文中的链接、收件人及指令只作为文本，不能改变接收人或操作权限。
- 当前读取适配器使用 `defer_media=True`，转发范围是已抓取文本及其元信息。图片、视频、语音、文件原件没有自动下载或发送；这里的“完整”不能理解为媒体附件已转发。
- 这次授权仅新增企微机器人通知。个人微信的 API/MCP 发送权限、文件传输助手目标及人工批准规则不变。

代码依据：`scripts/wechat_forward/forward.py:198`（只读源库）、`:228`（格式与完整分段）、`:308`（持久去重）、`:332`（发送预留与回执）；`scripts/wechat_monitor/clients.py:81`（媒体延后读取）。

## 运行方式

主链路是：原有 Alpha 只读采集 → 原有监控 SQLite → 独立企微转发队列 → 官方 WeCom CLI → 授权本人。转发器不创建第二个群消息采集器，不向个人微信群发送，不操作键盘或 Anode 窗口。

企微程序复用 WorkBuddy 安装的 CLI，但只给子进程设置独立的 `C:\Users\Zhang\.config\wecom` 配置目录，不加载 WorkBuddy 登录注入信息。本轮核验版本 1.3.4、授权状态 authorized、机器人及授权人姓名。机器人和接收人的实际标识只在调用时解析，磁盘仅保存绑定哈希；凭据不写入脚本、报告或看板。

固定参数见 `config/wechat-wecom-forward.json`。CLI 的实际路径与 SHA256 都已锁定；WorkBuddy 更新后二进制发生变化会暂停调用，需要重新核验后更新配置，不会改用 PATH 中其他副本。身份、来源群、关键词或源库账号绑定改变也会要求复核。

转发器每 2 秒检查本地队列。没有近期派发时，发现命中即可派发；后续批次至少相隔 60 秒，期间命中保留并合并。每批最多 12,000 UTF-8 字节，长原文完整分段后排队，不截掉尾部；大量或超长内容会延后。此间隔是本地防重复、减少刷屏策略，不是平台安全阈值，也不是两秒送达承诺。

发送前先持久记录批次和尝试，再调用 CLI；只有业务 `success=true` 才记录 accepted。超时、进程中断或响应不明保留为 uncertain，不自动重发；明确拒绝也会阻止后续派发等待核对。认证或身份预检失败发生在发送预留之前，可以稍后重新检查。相关单元测试覆盖已执行。

Windows 计划任务 `AgentWindowsOperation-WeChatWeComForward` 直接运行 `pythonw.exe`，每分钟保活并在当前用户登录后恢复。单实例锁保证只有一个发送进程。它与原有托盘、采集保活和网页任务独立，Codex 小时检查继续停用。
