# Anode MCP 桥接与直连实测

核验日期：2026-11-04。结论：常用操作适合原生 MCP 接入。持续连接时桥接额外开销较小，每次新开 PowerShell 的开销明显。当前测试的 Code Mode 能发现全部 41 个工具，但初始请求没有展开这 41 个工具的完整定义。

限制：这是只读状态查询及工具加载测试。没有实测桌面 App 完整任务耗时、真实模型计费、GUI 操作质量或插件安装流程。下列结论限定于本机 Codex CLI 0.166.0、现有 gpt-6-astra 模型元数据的 code_mode_only 模式及 Anode MCP 0.11.3。

## 调用耗时

同一现有 Anode Session 6、同一个 seat_status、空参数。每条路径预热后各测 12 次，按固定随机顺序交替执行。每次均校验 state、agentReady、session、seat PID 和屏幕信息一致。

| 路径 | 中位数 | 最小值 | 最大值 |
|---|---:|---:|---:|
| 持续 stdio 直连 Anode MCP | 70.124 ms | 67.159 ms | 88.392 ms |
| 复用现有 HTTP/Python 桥 | 88.336 ms | 69.150 ms | 114.167 ms |
| 每次新开 PowerShell，再通过项目桥调用 | 689.030 ms | 653.736 ms | 768.215 ms |

热桥与直连的中位数差为 18.212 ms。新开 PowerShell 的路径与直连差为 618.906 ms。主要可见差距来自 shell 启动及调用包装，不能把这个倍数套到完整桌面任务上。

stdio 测速使用独立测试客户端，不是桌面 App 的端到端计时；另外已通过真正的 Codex 原生 MCP 连接各调用一次 seat_status，全部工具和单工具配置分别返回 ready，调用代码内计时为 113 ms、150 ms。每种只有一次，不能用它们推断工具数量对速度的影响。

直连 MCP 启动、initialize 和 tools/list 单次合计 307.281 ms；这不是启动 Windows 子会话的时间，也没有对应的桥冷启动对照。

## 41 个工具与上下文

用已安装的 Codex CLI 发出真实请求，模型端由本地固定响应程序代替。它依次返回预先写好的工具发现与只读查询调用，然后返回结束文本。没有调用真实模型，也没有把离线数值伪装成额度消耗。

| 临时配置 | 运行时发现的 Anode 工具数 | 初始请求展开的 Anode 完整工具定义 | 原生状态调用 |
|---|---:|---:|---|
| 不注册 Anode | 0 | 0 | 不调用 |
| 注册全部工具 | 41 | 0 | ready，Session 6 |
| 白名单只开放 seat_status | 1 | 0 | ready，Session 6 |

每种配置捕获两次请求。第一次尚未发现工具；通过 Code Mode 查询运行时工具目录后，第二次请求包含测试主动输出的名称清单、选中 seat_status 的一份详细说明及其真实调用结果。其余工具没有执行，也没有自动展开完整参数说明。

初始请求的共同输入内容用 o200k_base 离线计数约为 18.7k token；三种配置分别为 18,697、18,687、18,685。这里包含通用指令等内容及动态信息，不能把这些小差异解释为 Anode 的计费差异。Anode 的原始完整工具清单另计为 43,285 字符、9,775 个 o200k_base token；本次没有将整份清单作为初始工具说明发送。

据此，当前模式下可以原生注册全部 41 个工具，再按需读取说明。白名单可以管理可用功能，但本次没有出现“全注册就让每轮多塞约 9.8k token”的情况。更换客户端版本、模型或工具呈现模式后应重新验证。
